# Experiment Cycle — Execute, Monitor, Collect, Diagnose, Supplement

> **User request:** $ARGUMENTS

## ⚠️ CRITICAL RULES

1. **ALL files under `.research/`** — never write to project root.
2. **Experiments via `research_experiment(action="register")`** — writes to `.research/experiments/`. **NEVER run training/eval without registering first.** Quick registration: `research_experiment(action="register", title="...", idea_ref="...", plan_ref="...")`. Register BEFORE running code, `research_experiment(action="complete", id="exp_XXX", metrics={...})` after. Unregistered experiments break pipeline traceability and claim evidence chains.
3. **Commit code before submitting any experiment** — see `references/git-discipline.md`.
4. **Subagents return text, not files.** Each dispatch includes file guidance for the agent type.
5. **Follow AGENTS.md at project root** — directory structure, naming, no v1/v2/v3, use venv, TDD.
6. **Long-running tasks use nohup + agenda_watch** — NEVER bash-wait. Logs go to `logs/`.
7. **Gate 1 (Code Gate)**: After writing/modifying experiment code, dispatch `inspector` subagent to audit code quality BEFORE git commit. Fix all issues and repeat until clean.
8. **Record results immediately** — when an experiment completes, call `research_experiment(complete)` with metrics.
9. **Ingest knowledge** — relevant papers, insights, and decisions → `research_wiki` and `research_timeline`.
10. **Gate 2 (Design Gate)**: Declare red-lines at registration. Dispatch `auditor` subagent before registration AND after completion to verify R1-R7. Experiment cannot complete until all red-lines pass.
11. **Evidence authenticity**: Every experiment must declare its authenticity level (prototype/pilot/evidence). Prototypes and pilots cannot support claims. Only evidence-grade experiments can support claims. Prototypes can be marked complete for reference but carry no evidentiary weight.
12. **NO MID-BATCH PIVOT**: When an experiment batch is running, you will inevitably discover new ideas, alternative approaches, or interesting side results. **Do NOT act on them immediately.** Instead: (a) Record the idea as a journal note via `research_journal(action="append", kind="opportunity_spotted", note="...")` — this preserves it without derailing. (b) Finish ALL registered experiments in the current batch first (complete or fail each one). (c) Only AFTER the batch is fully resolved, review accumulated opportunity notes and decide whether to iterate within experiment phase or formally redirect to an earlier phase (design/ground/explore) via `research_state(action="redirect")`. Mid-batch pivots are the #1 cause of direction drift and unfinished experiments.
- **Every session ends with** `research_state(action="brief")` — ensures state is persisted and monitor reflects current status

A research project that spans weeks/months MUST run on a single project-specific Docker image with all dependencies baked in. Reusing generic platform images (`pytorch2.5-cuda12.4`, etc.) breaks reproducibility — platform images get updated, removed, or silently changed over time, so experiments from last month cannot be rerun.

Only if the experiment is a single trivial check (e.g. `python -c "import torch; print(torch.cuda.is_available())"`) may a platform image be used. Anything registered via `research_experiment(action="register")` requires a project image.

## Step 1: Register Experiments

Each experiment produces evidence. Before registering, classify its authenticity:

prototype — synthetic data, homemade evaluator, tiny subset. For debugging only. Cannot be marked complete.
pilot — real data at reduced scale. For direction validation. Cannot support claims.
evidence — full benchmark, official evaluator, complete scale. Can support claims.

Only evidence-grade experiments can support claims in the paper. Prototypes and pilots are valuable for debugging and validation but do not constitute proof.

From the plan's experiment matrix, register each experiment:

```
research_experiment(action="register",
  title="Main method — seed 42",
  group="main",
  plan="plan_002",
  idea="idea_XXX",
  backend="inspire",
  authenticity="evidence",
  redlines=["R1_metric_immutability", "R3_no_data_leakage", "R4_honest_reporting", "R5_dataset_integrity", "R6_reproducibility"],
  domain_constraints=["Must use Qwen2.5-7B backbone for fair comparison"],
  hyperparameters={learning_rate: 1e-4, batch_size: 128, seed: 42},
  content="## Setup\n\nBaseline comparison with learning_rate=1e-4.\n\n## Success Criteria\n\nBeat baseline PPL by >1.0 point.")
```

### Registration order

Follow the plan's priority structure:

| Group | Priority | Register when |
|-------|----------|---------------|
| `sanity` | 1st | Always — verify basic assumptions first |
| `baselines` | 2nd | Always — needed for comparison |
| `main` | 3rd | After sanity passes |
| `ablations` | 4th | After main shows positive signal |
| `robustness` | 5th | After main results are stable |
| `stress` | 6th | Only if time/budget permits |

For multi-seed experiments, register each seed as a separate experiment:
```
research_experiment(action="register", title="Main method — seed 42", ...)
research_experiment(action="register", title="Main method — seed 123", ...)
research_experiment(action="register", title="Main method — seed 456", ...)
```

## Step 2: Submit to Compute Platform

### 2.0 Parallel-by-Default (MANDATORY)

Before submitting, identify ALL opportunities for parallel execution. Parallel-by-default applies within each experiment group — all experiments in the same group can run simultaneously. Sequential ordering applies between groups (sanity → baselines → main → ablations → robustness → stress).

What always runs in parallel (within the same group):
- All experiments in the same group (all sanity experiments together, all baselines together, etc.)
- Multiple seeds of the same experiment configuration
- Data preprocessing while experiments run
- API calls (batch or concurrent dispatch)
- Subagent dispatches (scholar, scout, critic, methodologist, auditor, inspector)

What must run sequentially (between groups):
- Later groups depend on earlier group results (main depends on baselines, ablations depend on main)
- Code changes between experiments (experiment B requires code changes based on experiment A's results)
- Resource constraints (GPU quota limits concurrent jobs)

If experiments are running sequentially within the same group, ask: "Why can't these run together?"

### 2.1 Workspace Decision (MANDATORY)

**BEFORE submitting: Load `references/inspire-compute.md`** for the full workspace selection policy, image building strategy, and pre-build philosophy.

**Full policy: `references/inspire-compute.md`. Four rules:**

- **GPU** → run `inspire_status()`, pick from your project's available GPUs (prefer higher VRAM for large models, any idle GPU for pilots)
- **CPU** → Local `bash` if < 30 min, `CPU资源空间` (low priority) if longer, HPC only for multi-node
- **Image must be pre-built** — all deps baked into the image. Never `pip install` at runtime.
- **Instance type** → `inspire_submit` (training task) for experiments. Never `inspire_notebook`.

### 2.2 Inspire Backend (GPU training)

```
# Single-GPU pilot (has internet):
inspire_submit(
  name="exp_007",
  command="source /opt/conda/etc/profile.d/conda.sh && conda activate myenv && cd /inspire/hdd/project/{en_name}/code && python train.py --config configs/pilot.yaml --seed 42 2>&1 | tee /inspire/hdd/project/{en_name}/logs/exp_007.log",
  workspace="<from inspire_status>",
  compute_group="<from inspire_status>",
  spec="<from inspire_status>",
  image="docker.sii.shaipower.online/...",
  priority=9)

# Large/multi-GPU (offline — NO internet):
inspire_submit(
  name="exp_008",
  command="source /opt/conda/etc/profile.d/conda.sh && conda activate myenv && cd /inspire/hdd/project/{en_name}/code && python train.py --config configs/large.yaml --seed 42 2>&1 | tee /inspire/hdd/project/{en_name}/logs/exp_008.log",
  workspace="<from inspire_status>",
  compute_group="<from inspire_status>",
  spec="<from inspire_status>",
  image="docker.sii.shaipower.online/...",
  shm=65536,
  priority=9)
```

**Constraints that affect submission correctness:**

- **Do NOT use `inspire_config(commandPrefix=...)`**: Synergy-wide global — changing it breaks ALL other research projects. Write the full `source /opt/conda/etc/profile.d/conda.sh && conda activate myenv && cd /inspire/hdd/project/{en_name}/code && python train.py` inside every `command`.
- **Offline space** (`分布式训练空间`): NO internet. Commands must NOT contain `pip install`, `git clone`, `wget`, or any network operations. All deps must be in the pre-built image.
- **Non-interactive shell**: `~/.bashrc` is NOT loaded. Always `source /opt/conda/etc/profile.d/conda.sh && conda activate myenv`.
- **Shared memory**: Multi-GPU training requires `shm ≥ 65536` (64GB). Single-GPU can use defaults.

See `references/inspire-compute.md` § Common Pitfalls for image domain, log capture, GPU regions, and troubleshooting.

## Step 3: Monitor Running Experiments

The monitoring flow has two phases:
1. **Initial check** (Steps 3.1-3.3): Verify experiments launched correctly — run once after submission
2. **Async watch** (Step 3.4): Set up watches for long-running jobs, then yield the session. You will be woken when status changes.

### 3.1 Status check

For each running experiment:

```
inspire_jobs(status="running")
inspire_metrics(job_id="job-xxx", time_range="30m", mode="summary")
inspire_logs(job_id="job-xxx", lines=50)
```

### 3.2 Health assessment

| Signal | Healthy | Warning | Critical |
|--------|---------|---------|----------|
| GPU utilization | > 70% | 30-70% | < 30% sustained (> 15 min) |
| Loss trend | Decreasing | Plateaued | Diverging / NaN |
| Memory usage | < 90% | 90-95% | OOM risk |
| Training speed | Expected | Slower than expected | Stalled (no output > 10 min) |

### 3.3 Handle critical issues

If critical signals detected:

1. Read full log: `inspire_logs(job_id="job-xxx", lines=500)`
2. Diagnose: OOM → reduce batch size; NaN loss → check learning rate / gradient clipping; GPU idle → data loading bottleneck
3. **Report to user immediately** — do not wait for the job to fail
4. If clearly unrecoverable: `inspire_stop(job_id="job-xxx")`

### 3.4 Watch for experiment completion

For long-running jobs, set up a watch that wakes you when the job finishes:

```
agenda_watch(
  title="Monitor exp_007 (job-xxx)",
  delay=config.experiment.monitor_interval,
  prompt="Check experiment exp_007 (job-xxx) status via inspire_jobs and inspire_logs.
    If completed: collect results via inspire_logs, then run red-line audit (Step 4.4) before recording complete.
    If failed: record failure via research_experiment(action='fail'), check references/auto-retry.md for recovery, and set a new watch if retrying.
    If still running: set another agenda_watch with delay='30m' to check again.")
```

**Multiple experiments**: Set one watch per job. Each fires independently when its delay elapses.

```
agenda_watch(title="Monitor exp_007", delay="30m", prompt="Check exp_007 (job-007)...")
agenda_watch(title="Monitor exp_008", delay="30m", prompt="Check exp_008 (job-008)...")
agenda_watch(title="Monitor exp_009", delay="30m", prompt="Check exp_009 (job-009)...")
```

After being woken up by a watch:
- Read the prompt context to recall which experiment this is about
- Check status: `inspire_jobs()` + `inspire_logs(job_id="...", lines=50)`
- If experiment completed → proceed to **Step 4.1** (collect results), then **Step 4.4** (red-line audit) before marking complete
- If experiment failed → proceed to **Step 4.2** (record failure), then check `references/auto-retry.md`. After retrying, **set a new watch** for the retry job.
- If still running → set a new `agenda_watch` with appropriate delay
- Check if other experiments are still running — if all done, proceed to Step 5

Do NOT use `agenda_schedule` with `type: "every"` for experiment monitoring — that creates a new agent session every interval, wastes tokens, and may not auto-stop.

### 3.5 Detect stuck/idle jobs

If GPU utilization < 10% for > 15 minutes:
1. Check if in data-loading phase (may be normal)
2. Check logs for errors or hangs
3. If truly stuck: stop and report
4. Update: `research_experiment(action="stop", id="exp_XXX")`

### 4.1 Success

```
inspire_logs(job_id="job-xxx", lines=200)  // read final output
```

```
research_experiment(action="complete", id="exp_XXX",
```

### 4.2 Failure

```
  failure_reason="OOM at step 8000, batch_size=128 too large for 40GB GPU",
  notes="Root cause: activation memory spike at layer 28 during backward pass. Fix: reduce batch_size to 64 or enable gradient checkpointing. Will retry as exp_XXX+1.")
```

The `notes` param records the failure analysis directly — no separate edit needed.

### Diagnosis Levels (L1-L6)

| Level | Name | Focus | Example |
|-------|------|-------|---------|
| L1 | Code Bug | Implementation error | Off-by-one, wrong API usage |
| L2 | Data Bug | Data pipeline issue | Wrong features, data leak |
| L3 | Eval Bug | Evaluation protocol error | Wrong metric, train/test leak |
| L4 | Method Limitation | Fundamentally limited on this problem | Model too simple, wrong inductive bias |
| L5 | Scope Mismatch | Problem formulation doesn't match method | Wrong objective, missing constraints |
| L6 | Fundamental Impasse | Irreconcilable conflict | Contradictory requirements, infeasible constraints |

L1-L3 → rollback to realize (code/data/eval fixes). L4-L5 → rollback to design (method redesign). L6 → rollback to ground/explore (reformulate).

### Anti-Give-Up Rule (v2.1)

Before any method-failure pivot, the phase run must show:
1. L1-L6 report completed
2. At least one implementation review or justification for skipping
3. At least min_seeds or explicit evidence that more seeds are wasteful
4. RQG failure is not caused by metric, data, or benchmark mismatch
5. Human checkpoint confirmed (or waived in autonomous mode)

Diagnosis routing:
- L1-L3 fail → pivot to realize (code/data/eval bugs)
- L4-L5 fail → iterate experiment (hp sweep, more seeds)
- L6 fail → pivot to ground (story/benchmark mismatch)
- L1-L6 pass but RQG strongly fails → pivot to design (method failure)

### 4.3 Invalidation

When an experiment completes but results are unreliable:

```
research_experiment(action="invalidate", id="exp_XXX",
  invalidation_reason="Data leakage detected: validation set overlapped with training due to preprocessing bug in commit abc123")
```

This is different from failure — the experiment ran to completion but the results cannot be trusted.

### 4.4 Results Audit (Gate 2 — Post-completion)

For each completed experiment, dispatch auditor to verify red-lines BEFORE marking complete:

```
task(subagent_type="auditor", description="Red-line audit for exp_XXX",
  prompt="Audit experiment exp_XXX for red-line compliance.

  Read:
  - .research/experiments/exp_XXX.yaml (declared red-lines, metrics, config)
  - .research/experiments/exp_XXX.md (experiment notes)
  - The experiment code and eval scripts
  - Git log for the experiment period

  For each declared red-line, verify independently:
  R1: Was the eval metric changed after seeing results?
  R2: Were eval code changes followed by full re-runs?
  R3: Any sign of test data leakage?
  R4: Are all seeds reported? Any cherry-picking?
  R5: Is the data split documented and consistent?
  R6: Is the code committed and reproducible?
  R7: Are domain constraints satisfied?

  Report: PASS/FLAG/VIOLATE for each rule with evidence.")
```

After auditor returns:
- Update red-line status: `research_experiment(action="update", id="exp_XXX", redline_status={R1: "passed", ...})`
- If all pass → mark complete: `research_experiment(action="complete", id="exp_XXX", metrics={...}, notes="...")`
- If any violated → mark invalidated: `research_experiment(action="invalidate", id="exp_XXX", invalidation_reason="Red-line violation: R3 — test data leakage detected")`

Mark `audit-results` DAG node completed only after all experiments in the batch pass red-line audit.

## Step 5: Result Analysis

### 5.1 Cross-experiment comparison

After ≥2 experiments in the same group complete:

```
research_experiment(action="compare", ids=["exp_001", "exp_005", "exp_007"])
```

### 5.2 Statistical rigor

Statistical testing thresholds from `config.experiment`: `significance_level` (default: 0.05), `min_seeds` (default: 3).

| Seeds available | Required test | Interpretation |
|----------------|--------------|----------------|
| ≥ `config.experiment.min_seeds` | Paired t-test (normal) or Wilcoxon signed-rank (non-normal) | Report p-value and Cohen's d |
| 1-2 | Bootstrap CI (1000 resamples) | If CI crosses zero → inconclusive |
| 1 | Do NOT claim improvement | Report as preliminary observation only |

Annotate each comparison:
- ✅ p < 0.05 AND Cohen's d > 0.5 → meaningful improvement
- ⚠️ p < 0.05 but Cohen's d < 0.5 → significant but small effect
- ❌ p ≥ 0.05 → no reliable improvement

### 5.3 Negative result analysis

Failed and negative-result experiments are data, not waste. For each:
- What was the hypothesis?
- What went wrong?
- What does this tell us about the approach?
- Should this change the plan?

Record insights:
```
research_timeline(action="append_free_event", event_type="insight",
  summary="Root cause: gradient detachment in residual branch prevents end-to-end learning",
  event_refs=["exp_005"])
```

## Step 7: Supplement Experiments

After analyzing results, determine if the evidence package is sufficient:

### 7.1 Check against plan's evidence sets

- **Kill set passed?** All kill-set experiments completed and results are positive → method works
- **Kill set failed?** Any kill-set experiment clearly negative → method may not work → consider rollback to `design`
- **Sufficient set complete?** All sufficient-set experiments passed → ready for `compose` phase (invoke claim-build)
- **Sufficient set incomplete?** Missing experiments or inconclusive results → supplement

### 7.2 Common supplements needed

| Gap | Supplement | Priority |
|-----|-----------|----------|
| Insufficient seeds | Add 2-3 more seeds for key results | HIGH |
| Missing baseline | Add the strongest recent baseline | HIGH |
| Missing ablation | Isolate the core component | HIGH |
| Robustness untested | Vary dataset/scale/hyperparameter | MEDIUM |
| Edge cases unknown | Design stress test | LOW |

Register and submit supplement experiments following Steps 1-4.

### 7.3 Evidence sufficiency assessment

Use the `methodologist` subagent to assess whether the current evidence package supports the planned claims:

```
task(subagent_type="methodologist"):
  "Review the current experiment results against the planned claims:

   Plan: [paste plan's claim-driven validation sketch]
   Completed experiments: [list with metrics]
   Failed/invalidated experiments: [list with reasons]

   Assess:
   1. Which planned claims are now supported by evidence?
   2. Which claims lack sufficient evidence?
   3. What specific experiments would fill the remaining gaps?
   4. Is the evidence package sufficient to proceed to the compose (claim-build) phase?

   Be concrete about what's missing and what would fix it.
   Return your analysis as structured text."
```

## Step 9: Advance or Rollback

### 9.1 Paper Ambition Checkpoint

**⏸ CHECKPOINT — do not proceed without user input.**

**Checkpoint kind: `paper_ambition`**

Before transitioning to compose phase, the user must confirm result quality and claim strength.

Present:
- Kill set status (passed / failed)
- Sufficient set status (complete / incomplete)
- RQG evaluation (passed / partial / failed)
- L1-L6 diagnosis summary
- Key metrics with statistical significance
- Red-line audit results
- Claim strength assessment (strong / moderate / weak)
- Recommended paper ambition level

**Options for user**:
1. **Advance to compose** — results support the planned claims; proceed to paper writing
2. **Strong claim** — RQG passed, evidence is strong
3. **Moderate claim** — RQG partial, evidence is solid but has caveats
4. **Weak claim / exploratory** — limited evidence, paper should be scoped narrowly
5. **Request more experiments** — supplement specific gaps before composing
6. **Pivot to realize** — DiagnosisReport points to implementation bug
7. **Pivot to design** — L1-L5 pass but method signal is weak
8. **Pivot to ground** — L6 shows benchmark/story mismatch

Record user decision rationale in journal.
**In autonomous mode**: Agent may waive but MUST log waiver with reasoning to `phase_run.human_checkpoints`.

When a human checkpoint is triggered, the system auto-generates a checkpoint brief. The brief provides full context for the human decision. If you need to regenerate or view it, use `research_checkpoint_brief(action="generate"|"read")`.

## Participation Mode Behavior

- **collaborative**: Confirm each experiment submission. Report every completion/failure. Pause before supplementing. Pause before advancing/rolling back.
- **guided**: Confirm first experiment only. Auto-submit subsequent same-type experiments. Report completions in batches. Pause before advancing/rolling back.
- **autonomous**: Submit all planned experiments. Auto-supplement based on evidence assessment. Only pause on: all experiments fail, red-line violations detected, rollback needed.

## Error Recovery

| Situation | Action |
|-----------|--------|
| Inspire submission fails | Check `inspire_status` for resource availability. Try different compute group, lower priority, or smaller spec. |
| Job dies immediately | Read `inspire_logs`. Common: wrong image, missing conda, data path incorrect, CUDA version mismatch. Fix and resubmit with same exp ID. |
| Docker build fails | Switch to `buildah bud --isolation chroot -t image:tag -f Dockerfile .` — see `references/inspire-compute.md` § Image Building |
| Image not found on platform | Image was pushed to Harbor but not registered. Go to 镜像管理 → 新建镜像. |
| Budget exhausted | Stop submitting. Report remaining experiments. Suggest: low-priority CPU tasks (free), reduce scope, or pause. |
| Job preempted | Check if checkpoint exists. If yes: resubmit with resume flag. If no: resubmit from scratch at higher priority. |
| Results inconsistent across seeds | Run additional seeds. If variance > 2× the improvement → the result is not reliable. |
| Experiment invalidated | Document reason. Register and run a clean replacement. |
| Red-line violation | Mark invalidated with violated rule. Fix root cause, then register clean replacement. |
| All kill-set experiments fail | This is a strong signal the method doesn't work. Recommend rollback to `design` with the failure evidence. |
| Code has uncommitted changes | REFUSE to submit. Commit first, then register the experiment with the correct code_commit hash. |
