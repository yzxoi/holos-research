## Step 1: Exhibit Planning

Before writing a single word, plan every figure and table the paper needs. Claims drive exhibit design — not the other way around.

### 1.1 Map claims to exhibits

For each final claim, determine what visual evidence supports it:

| Claim | Exhibit Type | Content | Priority |
|-------|-------------|---------|----------|
| Main result | table | Main comparison table (method vs baselines) | Must-have |
| Main result | figure | Training curves / convergence | Should-have |
| Ablation finding | table | Ablation results | Must-have |
| Analysis insight | figure | Visualization of the mechanism | Must-have |
| Robustness | table | Results across conditions | Should-have |

### 1.2 Plan supplementary exhibits

Supplementary material for Nature-level submissions typically needs:
- Extended result tables (full metrics, all datasets, all seeds)
- Additional ablations not shown in main text
- Implementation details as figures (system architecture, data pipeline)
- Failure case examples
- Hyperparameter sensitivity analysis

### 1.3 Register all exhibits

For each planned exhibit:

```

  title="Main comparison table",
  kind="table",
  label="tab:main_results")

  experiments=["exp_007", "exp_008", "exp_009"],

## Step 4: Section-by-Section Writing

**Load `references/writing-guide.md` for narrative strategies and section standards.**
**Load `references/prose-quality.md` for paragraph-level quality control.**

### Writing approach

- Use `scribe` subagent for initial drafts of each section (scribe returns text; main agent writes to `paper/` using the `write` tool)
- Provide scribe with: claim objects, exhibit descriptions, positioning matrix, method design, **broader insights from compose (claim-build)**
- After each section draft, review with `editor` subagent (editor returns text; main agent records via `research_paper(action="review")`)

### Section order (recommended)

Write in this order for maximum coherence:

1. **Method** — write first because it anchors the technical content
2. **Results** — write second because it directly renders the claims
3. **Introduction** — write third because now you know what the paper delivers
4. **Related Work** — load `lit-knowledge` skill for wiki data
5. **Discussion** — write honestly about limitations, broader perspective, and future work
6. **Abstract** — write last because it must accurately summarize everything
7. **Conclusion** — brief, forward-looking, no overclaim

### For each section:

```
task(subagent_type="scribe"):
  "Draft the [section name] section for a paper titled '[title]' targeting [venue].

   Key content:
   [section-specific material — claims, method design, experiment results, etc.]

   Constraints:
   [from writing-guide reference — tone, length, structure requirements]
   Return the drafted text. The main agent writes it to the correct location."
```

### Special instructions for Introduction:

When drafting the Introduction, provide scribe with the broader significance statement from the contribution positioning (novelty-ground) AND the broader insights from the compose (claim-build) phase. Include this directive:

> "After the contribution list and main result preview, include a paragraph that connects this work to the bigger picture. Draw on the broader significance and insights provided. Ask: if this method works, what changes in how people approach [broader problem domain]? Be specific — name the community, the assumption being challenged, the capability being unlocked. Do NOT use generic phrases like 'opens new research directions' — state the specific direction."

### Special instructions for Discussion:

When drafting the Discussion, include this directive:

> "Include a 'Broader Perspective' paragraph before limitations. This paragraph positions the work within the trajectory of the field. Use the validated insights from the compose (claim-build) phase. What does this result suggest about [the fundamental question underlying the research]? What established assumption does it challenge or confirm? What new questions does it open — not implementation tasks, but genuine research questions? Write this for a reader who works in an adjacent area and wants to know why your finding matters to them."

After draft:
```
task(subagent_type="editor"):
  "Review this draft [section name] section:
   [paste draft]

   Check: clarity, logic flow, claim-evidence alignment, honest scope,
    venue-appropriate tone and length.
    Return your editorial feedback as structured text with specific location references."

Record paper-level review:
```
research_paper(action="review", id="paper_001",
  reviewer="editor", focus="[section] narrative quality", ...)
```

## Step 5: Prose Quality Audit + Narrative Coherence

**Load `references/prose-quality.md` for the full 5-pass audit protocol.**

### 5.1 Run the 5-pass prose quality audit

For each section, apply (in order):
1. **Clutter extraction** — remove filler phrases, redundancies, AI-isms
2. **Active voice check** — convert passive, resurrect smothered verbs
3. **Sentence architecture** — split >40 word sentences, fix subject-verb distance
4. **Keyword consistency** — verify technical terms are used identically everywhere (the Banana Rule)
5. **Numerical integrity** — verify numbers in text match tables/figures

Use `editor` agent for passes 1-4, `auditor` agent for pass 5.

### 5.2 Reverse outline test

Extract the first sentence of every paragraph and read them in sequence. They should form a coherent story: problem → gap → method → evidence → conclusion. Fix any paragraphs whose topic sentence doesn't advance the narrative.

### 5.3 Full-paper coherence check

After all sections are drafted and quality-audited, do a full-paper coherence check:

```
task(subagent_type="editor"):
  "Review the complete paper draft for narrative coherence:

   [paste full paper or provide file path]

   Check:
   1. Does the introduction promise exactly what the paper delivers?
   2. Does each claim in the results trace to the method section?
   3. Is related work fair and complete?
   4. Are limitations honest?
   5. Is the abstract accurate?
   6. Are cross-references consistent (figures, tables, equations, sections)?
   7. Is the writing style consistent throughout?
   Return your editorial feedback as structured text with specific location references."
```

Record:
```
research_paper(action="review", id="paper_001",
  reviewer="editor", focus="full paper coherence", ...)
```

## Step 8: Advance to Ready

### 8.1 Submission Readiness Checkpoint

**⏸ CHECKPOINT — do not proceed without user input.**

**Checkpoint kind: `submission_readiness`**

Before marking the paper ready or advancing to submission, the user must confirm submission readiness.

Present:
- Section completion status
- Exhibit approval status
- Claim-exhibit binding coverage
- Page count and venue limit
- Claim strength classification (strong/moderate/weak per claim)
- RQG-backed evidence summary
- Known remaining issues
- Overclaim check status

**Options for user**:
1. **Mark ready for submission** — paper is complete and accurate
2. **Request revisions** — specific sections or claims need work
3. **Add more experiments** — evidence gap identified during writing
4. **Reduce claim strength** — downgrade strong claims to moderate/weak
5. **Park for later** — not ready to submit now

Record user decision rationale in journal.
**In autonomous mode**: Agent may waive but MUST log waiver with reasoning to `phase_run.human_checkpoints`.

When a human checkpoint is triggered, the system auto-generates a checkpoint brief. The brief provides full context for the human decision. If you need to regenerate or view it, use `research_checkpoint_brief(action="generate"|"read")`.

## Error Recovery

| Situation | Action |
|-----------|--------|
| Writing exposes unsupported claim | Rollback to compose (claim-build): `research_state(action="redirect", target_phase="compose", reason="Writing revealed unsupported claim: ...")` → then invoke claim-build skill |
| Exhibit data inconsistent | Re-verify with auditor. If experiment data is wrong, rollback to `experiment`. |
| Page limit exceeded | Prioritize: move content to supplementary, compress tables, tighten prose. Do NOT remove claims — move supporting evidence to appendix. |
| Section draft quality too low | Re-run scribe with more context. Use editor for specific feedback. Iterate. |
| Missing baseline comparison | Rollback to `experiment` to add the missing baseline. |
| User/editor gives feedback on existing draft | Route to `paper-revise` skill for targeted section-level revision: `skill(name="paper-revise")` |
