## Step 1: Technical Gap and Route Selection

### 1.1 Scan grounding material

From the wiki papers and idea positioning, extract:

- What mechanism do current methods use?
- Where exactly do they fail for this problem?
- Which recent techniques are relevant?
- What training objectives, representations, or interfaces are reusable?
- What details distinguish a real method from a renamed high-level idea?

### 1.2 Active search if needed

If local material is insufficient, use `mcp__scholight__search_papers` for discovery (replaces the legacy arXiv search): focused natural-language query, `strength: "thorough"`, `limit: 10`, `date_from`/`date_to` for the 2025-2026 window. Fall back to websearch/webfetch on arxiv.org or the arXiv search tool only if scholight is unavailable.

```
task(subagent_type="scholar", background=true):
  "Find the most recent (2025-2026) methods that address [bottleneck].
   Use mcp__scholight__search_papers (strength='thorough', limit=10, date_from/date_to
   for the window). Focus on: mechanism, training setup, failure modes.
  For important papers (core relevance):
  1. Call research_wiki(action="ingest_paper", title="...", authors=[...], year=..., venue="...", arxiv="...", thesis="...", method="...", key_results="...", limitations="...", project_relevance="...") to register with content
  2. Download PDF via arxiv_download to .research/literature/papers/{arxiv_id}.pdf
  For minor papers: return title/arxiv/venue as text, main agent decides whether to ingest.
    Return: title, one-line method, key limitation, date."

task(subagent_type="scout", background=true):
  "Search for open-source implementations of [approach type].
   What training recipes and architectures do they use?
    Return: repo, method, key hyperparameters, dataset."
```

If scholar found new papers it didn't ingest, supplement:
```
research_wiki(action="ingest_paper", ...)
```

### 1.3 Make the gap operational

Do not stop at generic research questions. Specify:

1. Current pipeline failure point: Where does the baseline break?
2. Why naive fixes fail: Larger context, more data, prompting, memory bank — why aren't these enough?
3. Smallest adequate intervention: What is the least mechanism that could fix the bottleneck?
4. Frontier-native alternative: Is there a more current route using foundation-model-era primitives?
5. Core technical claim: What exact mechanism claim could survive top-venue scrutiny?
6. Required evidence: What minimum proof is needed?

### 1.4 Route selection

If two plausible routes exist:

- Route A: Elegant minimal — the smallest mechanism directly targeting the bottleneck
- Route B: Frontier-native — a more modern route using LLM/VLM/Diffusion/RL only if it gives a cleaner story

Decision criteria: which route becomes a stronger paper? Which has cleaner novelty? Which avoids contribution sprawl?

If both routes are weak, rethink the framing rather than combining them.

## Step 2: Design the Evidence Package

The method is a hypothesis. The evidence package proves or disproves it. Design both together — a method without evidence is speculation.

For each core claim, define the evidence that would convince a skeptical reviewer:
- What benchmark, at what scale, with what official evaluation protocol?
- What baseline comparison would make the improvement undeniable?
- What ablation would isolate the contribution from confounding factors?

Evidence must be:
- Real: actual benchmarks with actual data, not synthetic substitutes
- Reproducible: a stranger with your code and configs gets the same numbers
- Comparable: same data, same evaluator, same protocol as baselines
- Sufficient: enough scale and seeds that statistical claims are credible

The method and its supporting experiment design are co-dependent. Design all five dimensions together. The order below is a starting point — jump between dimensions as constraints from one inform another.

### Dimension 1: Method Design

The proposal must answer "how would we build this?" Concrete enough that implementation could start.

Cover all of these:

1. One-sentence method thesis: A falsifiable mechanism claim — "We hypothesize that X because Y, which would mean Z." The outcome must be genuinely uncertain; explain why you could be wrong. If you already know it works, the thesis is not sharp enough.
2. Boring explanation: What is the most likely boring explanation (confound, data leakage, weak baseline, prompt sensitivity, compute mismatch) for a positive result? How does the experiment design rule it out? If no boring explanation exists, explain why the hypothesis is genuinely uncertain rather than trivially true.
3. Contribution focus: One dominant + at most one supporting contribution
4. Complexity budget:
   - What is frozen / reused (backbone, tokenizer, pre-trained weights)
   - What is new (≤ `config.design.max_new_components` trainable components)
   - What tempting additions are intentionally excluded and why
5. System graph: Modules, data flow, inputs, outputs
6. Representation design: What latent / embedding / token / signal space
7. Training recipe: Data source, supervision, losses, weighting, stagewise vs joint
8. Inference path: How trained components are used at test time
9. Why the mechanism stays small: Why a larger stack is unnecessary
10. Frontier primitive usage (if any): Exact role — planner, teacher, critic, reward model, generator prior, search controller, or distillation source
11. Failure modes: What could go wrong and what fallback exists
12. Novelty argument: How this differs from closest work, why it's more than naming a module
13. Design rationale: For each key design choice (architecture, loss, training strategy, component selection), state why this choice over alternatives. No choice should be unexplained — "standard practice" is an acceptable rationale only with citation.

Concreteness test: If a qualified engineer could not start implementing from this design, it is not concrete enough. Iterate until it passes this test.

```
dagpatch({ nodes: [{ id: "method", status: "completed" }] })
```

## Step 3: Synthesize and Resolve Conflicts

### 3.1 Cross-dimension consistency check

After all six dimensions are designed, verify they are mutually consistent:

- Does the method's complexity budget match the infrastructure plan?
- Do the selected benchmarks directly test the method's core claims?
- Are baselines evaluated on the same benchmarks with the same metrics?
- Does the dataset design support the training recipe?
- Is the evaluation protocol consistent across all experiments?

### 3.2 Resolve conflicts

If dimensions conflict, resolve by priority:

- The method's core claim is the anchor — other dimensions serve it
- If a benchmark doesn't test the claim, change the benchmark, not the claim
- If infrastructure cannot support the method, simplify the method or increase resources
- If baselines are unavailable for a key comparison, document the gap

### 3.3 Dimension convergence gate

Before proceeding to write the proposal, verify:

- Every core claim has a specific benchmark that tests it
- Method thesis is falsifiable with a genuinely uncertain outcome
- Boring explanation is identified and the experiment design rules it out
- Design rationale is provided for each key design choice
- Every benchmark has documented SOTA numbers and expected improvement
- Baselines cover all major approach categories
- Primary metric directly captures the contribution
- Statistical methodology is specified (seeds, tests, reporting format)
- Infrastructure plan covers environment, reproducibility, and efficiency
- Experiment Matrix is complete with all applicable groups, hyperparameters, seed strategy, and per-group compute
- No dimension contains "we'll figure this out later"

If any check fails, iterate on that dimension until it is concrete.

## Step 5: Adversarial Method Review

This is the core refinement loop. Deploy the critic subagent:

```
task(subagent_type="critic", background=true, dag_node_id="review"):
  "You are reviewing a method-first research proposal for a top venue.

   Your job is NOT to reward extra modules, contribution sprawl, or giant benchmark checklists.
   Your job IS to stress-test whether the proposed method:
   (1) still solves the original anchored problem
   (2) is concrete enough to implement
   (3) presents a focused, elegant contribution
   (4) uses foundation-model-era techniques appropriately
   (5) is supported by adequate benchmarks, baselines, and evaluation
   (6) has a falsifiable thesis with a genuinely uncertain outcome
   (7) has identified the most likely boring explanation and the experiment rules it out
   (8) justifies each key design choice with rationale

   Review principles:
   - Prefer the smallest adequate mechanism over a larger system
   - Penalize parallel contributions that make the paper unfocused
   - If a modern route would produce a better paper, say so concretely
   - If already modern enough, do NOT force trendy components
   - Do not ask for extra experiments unless needed to prove core claims
   - Check that benchmarks directly test the claims, baselines are fair, and evaluation is rigorous

   Read the Problem Anchor first. If your suggested fix would change the problem
   being solved, call that out as drift.

   === PROPOSAL ===
   [paste full proposal from plan .md]
   === END PROPOSAL ===

   Score these dimensions (1-10):

   1. Problem Fidelity (12%): Does the method attack the original bottleneck?
   2. Method Specificity (16%): Concrete enough to implement?
   3. Contribution Quality (16%): One dominant mechanism claim, real novelty, no sprawl?
   4. Hypothesis Sharpness (8%): Is the thesis falsifiable? Is the outcome genuinely uncertain? Is the most likely boring explanation identified and ruled out by the experiment?
   5. Design Rationale (8%): Is each key design choice justified? Are alternatives considered? Or are choices asserted without explanation?
   6. Frontier Leverage (8%): Uses current primitives appropriately?
   7. Impact Potential (12%): If this method works as proposed, does it change how people
      think about the problem? Would other researchers build on it?
   8. Feasibility (8%): Can this be built with stated resources?
   9. Experiment Design Quality (8%): Are benchmarks appropriate, baselines fair,
          evaluation rigorous, and infrastructure adequate?
   10. Evidence Quality (4%): Are benchmarks real and current? Are official evaluators used?
          Is the scale sufficient? Would a skeptical reviewer accept this as proof?

       OVERALL SCORE (1-10): Weighted average of all 10 dimensions.

   For each dimension < 7:
   - Specific weakness
   - Concrete fix (interface / loss / training recipe / deletion / benchmark change)
   - Priority: CRITICAL / IMPORTANT / MINOR

   Also:
   - Simplification Opportunities: 1-3 ways to delete/merge/reuse. NONE if already tight.
   - Modernization Opportunities: 1-3 ways to replace old-school pieces. NONE if already modern.
   - Experiment Design Gaps: Any missing benchmarks, weak baselines, or evaluation flaws.
   - Drift Warning: NONE or explanation.
   - Verdict: READY (score ≥9, no drift, focused) / REVISE / RETHINK
   Return your review as structured text."
```

```
    experiment_design_quality: N, evidence_quality: N, overall: N
  },
  action_items=[...],
  review_body="<full review text>")
```

## Step 6: Parse Feedback and Revise

### 6.1 Stop condition

If overall score ≥ `config.design.score_threshold` AND verdict is READY AND no unresolved drift → skip to Step 8.

### 6.2 Anchor and simplicity check

Before making any changes:

1. Copy the Problem Anchor verbatim
2. Anchor check: Which suggestions would cause drift?
3. Simplicity check: What is the dominant contribution? What can be removed/merged/frozen? Which suggestions add unnecessary complexity?

### 6.3 Classify feedback

- Valid: Sharpen mechanism, simplify, modernize, or strengthen experiment design
- Debatable: Revise but explain reasoning
- Wrong / drifting / over-complicating: Push back with evidence

### 6.4 Revision bias

Always bias toward:
- Sharper central contribution
- Fewer moving parts
- Cleaner reuse of strong backbones
- More natural frontier leverage when it improves the paper
- Stronger experiment design (better benchmarks, fairer baselines, more rigorous evaluation)

Do NOT add parallel contributions to chase score. If reviewer requests another module, first ask whether the same gain comes from a better interface, distillation signal, or inference policy.

### 6.5 Write revised proposal

Create a new plan version: `research_plan(action="create", title="Method proposal v[N+1]", idea="idea_XXX", supersedes="plan_XXX", content="[full revised proposal with anchor + simplicity check prepended]")`. Supersession creates a new immutable plan — never edit an existing plan's .md.

Record the revision:
```
research_timeline(action="append_free_event", event_type="insight",
  summary="Method revised round N: <key change>",
  event_refs=["plan_XXX"])
```

### 6.6 Re-review

Send the revised proposal back to reviewer. Include: Problem Anchor, score history from prior rounds, and the full revised proposal (reviewer is stateless).

Repeat Steps 5-6 until:
- Overall score ≥ `config.design.score_threshold` AND verdict is READY AND no drift
- OR `config.design.max_review_rounds` reached

### 6.7 Negative progress detection

If score does not improve for 2 consecutive rounds:
- The method may need fundamental rethinking, not incremental revision
- Present the situation to the user
- Consider: rollback to ground (if contribution is unclear) or explore (if direction is weak)

## Step 8: Present to User

**⏸ CHECKPOINT — do not proceed without user input.**

**Checkpoint kind: `reasonableness_check` + `resource_commitment`**

Before transitioning to realize phase, the user must confirm the mechanism is worth implementing AND commit resources.

Present:
- Method thesis (one sentence)
- Contribution focus (dominant + optional supporting)
- Broader significance (from the contribution statement — why this matters beyond the immediate technical result)
- Complexity budget (what is new vs reused)
- Benchmark selection (which benchmarks, why, current SOTA, target improvement)
- Baseline coverage (which approach categories, are comparisons fair)
- Evaluation plan (primary metric, statistical methodology)
- Infrastructure plan (compute, reproducibility, efficiency)
- Experiment matrix summary (number of groups, total runs, key hyperparameters, seed strategy)
- Overall score and verdict from last review round
- Score history across all rounds (show convergence)
- Key remaining concerns (honest)
- Drift status (preserved / corrected / unresolved)
- Compute and timeline estimate

**Options for user**:
1. **Approve and advance to realize** — confirm mechanism is worth implementing
2. **Request revisions** — specific changes to method, benchmarks, or evaluation
3. **Rollback to ground** — contribution boundary is unclear; needs re-positioning
4. **Rollback to explore** — direction is not viable

**Resource commitment questions**:
- Confirm compute budget available for implementation and experiments
- Confirm timeline aligns with target venue deadlines
- Confirm team capacity for implementation

Record user decision rationale in journal.
**In autonomous mode**: Agent may waive but MUST log waiver with reasoning to `phase_run.human_checkpoints`.

When a human checkpoint is triggered, the system auto-generates a checkpoint brief. The brief provides full context for the human decision. If you need to regenerate or view it, use `research_checkpoint_brief(action="generate"|"read")`.

## Error Recovery

| Situation | Action |
|-----------|--------|
| Method is overbuilt | Apply simplicity check. Remove weakest component, test if core claim survives |
| Contribution sprawl | Collapse to one dominant contribution. Move extras to future work |
| Drift detected | Present both directions to user. Do not resolve unilaterally |
| Method fundamentally infeasible | Recommend returning to ground with feasibility evidence |
| Reviewers disagree across rounds | Take the intersection of valid concerns, not the union |
| MAX_ROUNDS without READY | Present best version with honest weaknesses. User decides |
| Negative progress (2 rounds no improvement) | Suggest rethink. May need rollback to ground or explore |
| Benchmark survey finds no suitable benchmarks | Either create a benchmark or reframe the claim. Document the gap. |
| Dataset requirements exceed available resources | Reduce scope, use synthetic data, or find smaller public datasets |
| Baseline code unavailable | Follow the decision tree in references/baseline-design.md |
| User wants to adjust approved plan | Route to method-iterate: `skill(name="method-iterate")` for feedback-driven revision |
| Context compaction mid-loop | Plan `.md` is the checkpoint. Re-read to recover state |
| Phase rollback from experiment | Re-enter at Step 5 with experiment feedback. Method may need adjustment |

---

## Rollback Entry Points

### From experiment (method doesn't work as expected)

1. Read `research_state` to understand the rollback reason
2. Read experiment results and failure analysis
3. Re-enter at Step 2 (re-concretize) or Step 5 (re-review) depending on severity
4. The failure information should drive a more focused revision
5. If method is fundamentally broken → consider rollback to ground

### From compose (evidence doesn't support claims)

1. Read claim analysis showing which claims are unsupported
2. Re-enter at Step 2 (experiment design) to redesign experiment requirements
3. May need to narrow claims rather than add more experiments

### From venue-cycle (reviewer demands method changes)

1. Read external reviewer comments
2. Re-enter at Step 2 or Step 5 depending on severity
3. External reviewer feedback should be treated as high-priority valid feedback
