## Core Principle: Start From Friction, Not Decoration

Novel ideas come from mismatches — not from "what clever thing can I add". Capture the mismatch first, then propose an intervention.

**High-value signals to hunt for:**
- Anomaly: a result that breaks the current model of the system
- Contradiction: paper A and paper B imply different stories
- Missing mechanism: a gain is reported, but the causal reason is unclear
- Brittleness: works in one regime, fails in another
- Missing measurement: a strong claim without the metric that would verify it
- Cross-domain resonance: a bottleneck from one area looks structurally similar to another

**Before proposing any method, ask:**
1. What hidden variable would make this observation unsurprising?
2. Which implicit assumption is probably false?
3. What evidence is missing that would distinguish between two explanations?
4. Is the bottleneck in representation, objective, search, feedback, or evaluation?
5. What is the simplest control that could explain the result away?

## Step 0: Problem Anchor

Before any survey work, freeze the research problem to prevent drift.

### 0.1 Clarify with the user

If the user has not already provided a clear problem statement, ask:

- **Bottom-line problem**: What is the core research challenge?
- **Must-solve bottleneck**: What specific weakness makes this problem worth attacking?
- **Non-goals**: What are we explicitly NOT doing?
- **Constraints**: Compute budget, deadline, target venue, available datasets
- **Success condition**: What evidence would confirm the problem is solved?

### 0.2 Reject overly broad directions

If the direction is too broad, ask the user to narrow. Suggest 2-3 concrete sub-directions.

### 0.3 Initialize state and set anchor

```
research_state(action="advance", target_phase="explore",
  anchor="<user's research direction in their own words>",
  summary="<one-line problem anchor>",
  reason="Starting exploration for: <problem>")
```

### 0.4 Recover prior knowledge

```
research_wiki(action="query", query="<research direction>", limit=5)
```

### 0.5 Drift check protocol

Throughout the skill, after every major step, verify: does this still address the anchored problem?

## Step 2: Wonder Signal Extraction

**This is the key differentiator from v2.1.** Instead of jumping from gap analysis to generic ideation, first extract and sharpen the friction signals.

### 2.1 From survey to wonder log

Go through the survey findings and extract every signal that doesn't fit:

| Signal Type | Source | What doesn't fit | Why it matters | Next check |
|-------------|--------|------------------|----------------|------------|
| Anomaly | Paper X reports Y | Expected Z based on theory | Would mean [assumption] is wrong | Test [specific thing] |
| Contradiction | Paper A vs Paper B | A says X helps, B says X hurts | Different conditions? Missing variable? | Control for [variable] |
| Missing mechanism | Paper C | Gain reported without explanation | If we knew why, we could amplify or predict it | Ablate [component] |
| Brittleness | Method D | Works on X, fails on Y | Regime split → different bottleneck | Characterize the boundary |
| Missing measurement | Paper E | Strong claim without verification metric | The metric that would falsify is absent | Run the missing metric |

### 2.2 Sharpen each signal

For each wonder signal, ask:
1. What hidden variable would make this unsurprising?
2. Which implicit assumption is probably false?
3. What is the simplest control that could explain it away?

If a signal survives sharpening, it becomes a **seed for ideation**.

## Step 3: Wonder-Driven Idea Generation

Deploy **3 parallel agents**, each with a different creative lens. All three receive the Problem Anchor and wonder signals, but approach differently:

### Agent 1 — Wonder-driven mechanism hypotheses

Generate ideas by **sharpening wonder signals into mechanism hypotheses**. For each signal:
1. Propose what hidden variable, broken assumption, or missing measurement would explain it
2. Design the **smallest intervention** that targets the bottleneck
3. Design the **decisive test** that could kill the idea

Focus on: anomaly explanations, hidden variable reveals, regime splits, re-grounding comparisons.

### Agent 2 — Cross-domain structural transfer

Generate ideas by borrowing **only the core causal primitive** from another field — not the whole surface method. Only transfer when the bottleneck is actually the same structural problem.

Focus on: representation mismatches, objective mismatches, search geometry, feedback loop structures.

### Agent 3 — Contrarian / diagnostic

Generate ideas that **challenge assumptions** or **invert claims**:
- When should the celebrated mechanism fail, saturate, or become unnecessary?
- What diagnostic tool would expose the real failure mode?
- What benchmark is hiding the real problem?

### Idea format (include in each prompt):

```yaml
- title: [5-10 word name]
- core_insight: [one sentence — what hidden variable or broken assumption]
- wonder_signal: [which anomaly/contradiction/missing measurement this comes from]
- anchor_alignment: [one sentence: how this addresses the research anchor]
- differs_from: [cite_key, how it differs]
- contribution_type: [new_method | new_analysis | new_problem | method_transfer | diagnostic]
- idea_operator: [reveal_hidden_state | repair_interface | add_regrounding | split_regimes | challenge_metric | transfer_causal_primitive | invert_claim]
- risk_level: [LOW | MEDIUM | HIGH]
- simplest_intervention: [minimum change that targets the bottleneck]
- decisive_test: [smallest experiment that could kill the idea]
- simplest_baseline: [obvious control or prompt baseline]
- null_result_teaches: [why the test is still decision-relevant if it fails]
- story_spine:
    field_assumption: [what does the field currently assume?]
    pain_point: [what specific failure does this create?]
    non_obvious_insight: [the surprising mechanism or connection]
    why_now: [what changed to make this possible or urgent?]
    what_changes_if_true: [who benefits and how does practice shift?]
- candidate_paper_angles:
    - [type 1]
    - [type 2, different from first]
- impact:
    tier: [paradigm | enabler | incremental]
```

### Generation rules (include in each prompt):

- Every idea must trace back to a wonder signal — no "what if we combined X and Y" without a friction point
- Reject ideas that collapse into: "missing baseline", "untested setting", "a stronger prompt probably does it", or "complexity increase without isolated bottleneck"
- Keep only ideas whose **positive or negative outcome would change understanding or decisions**
- `anchor_alignment` is mandatory — if you can't write a convincing one-sentence alignment, drop the idea
- StorySpine is mandatory — if any field is weak, push back for concretization
- Every top idea must have ≥2 candidate_paper_angles (different contribution types)
- Maximize methodological diversity — avoid variations on a single theme

### Novelty filter (apply to each idea before registering)

Demote or reject if it is mostly:
- "paper X did not test setting Y" — unless the setting reveals a mechanism
- a prompt variant masquerading as a method
- a complexity increase without a clearly isolated bottleneck
- a benchmark-only gain that would not change decisions
- a story whose strongest baseline is still undefined

Keep if it clarifies mechanism, changes deployment decisions, or reveals a previously hidden failure boundary.

After all 3 agents return, merge into a single candidate pool (typically 12-18 ideas).

## Step 4: Convergent Filtering and Registration

### 4.1 Anchor alignment check

For each idea:
- **ALIGNED**: Directly addresses the anchor. Keep.
- **ADJACENT**: Related but different mechanism. Keep only if novelty is exceptional.
- **DRIFTED**: Does not address the anchor. Remove.

### 4.2 Quality filtering

Remove:
- Duplicates or near-identical ideas
- Ideas in the banlist
- Ideas without a concrete wonder signal origin
- Ideas where `simplest_baseline` would probably explain the result

### 4.3 Register surviving candidates

```
research_idea(action="create", title="<title>", content="## Core Insight\n\n[key insight]\n\n## Wonder Signal\n\n[anomaly/contradiction that inspired this]\n\n## Novelty Analysis\n\n[what makes this different]\n\n## Idea Operator\n\n[which operator was applied]\n\n## Decisive Test\n\n[smallest experiment that could kill the idea]\n\n## Feasibility\n\n[GPU hours, data, risks]")
```

## Step 5: Per-Claim Novelty Check

For the top 5-8 candidates, verify novelty per claim (same as v2.1 — parallel scholar dispatches).

### 5.1 Build novelty summary table

| Idea | Claim A | Claim B | Overall |
|------|---------|---------|---------|
| idea_001 | SCOOPED | Novel | PROCEED WITH CAUTION |
| idea_003 | Novel | Novel | Strong novelty |

### 5.2 Ruling

- ALL claims scooped → `research_idea(action="reject")`
- SOME claims scooped → keep as `exploring`, note which claims need redesign
- NO claims scooped → strong novelty, top candidate

### 5.3 Time-sensitivity check

For each "novel" claim, verify no concurrent work in the last 3 months.

## Idea Operators Reference

When generating ideas, apply one or more of these operators on a strong observation:

1. **Reveal hidden state**: Add the measurement or probe that would expose the suspected latent factor
2. **Repair interface mismatch**: Align representation, planner, verifier, or objective when they optimize different things
3. **Add re-grounding**: Compare open-loop execution against periodic correction or refreshed observations
4. **Split regimes**: Replace one averaged claim with a map of where the method helps, is neutral, or hurts
5. **Challenge the metric**: Test whether the benchmark score hides the true failure mode
6. **Transfer the causal primitive**: Borrow only the core mechanism from another field, not the whole surface method
7. **Invert the claim**: Ask when the celebrated mechanism should fail, saturate, or become unnecessary

## Error Recovery

| Situation | Action |
|-----------|--------|
| No wonder signals found | Literature may be too sparse — broaden survey or switch to `lit-knowledge` skill |
| No ideas survive novelty check | Report with full banlist. Suggest: broaden scope, combine partial ideas, re-survey |
| User rejects all ideas | Ask for specific feedback, return to Step 1 with adjusted scope and updated anchor |
| All ideas are incremental | The anchor may need reframing — the problem itself may not have a high-impact angle |
| Pilot experiments fail | Mark as inconclusive, rely on novelty + feasibility scores |
| Reviewer and main agent disagree | Present both assessments for user adjudication |
| Problem Anchor drifts | Flag immediately. Present original and drifted direction for user choice |
