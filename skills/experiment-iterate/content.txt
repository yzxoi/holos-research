### 0.3 Gap analysis

| exp_001 | main | completed | PPL | < 20.0 | 21.3 | +1.3 | Below target |

| exp_003 | ablation | completed | PPL | > exp_001 | 20.8 | -0.5 | Ablation shows component helps |

### 0.4 Identify the optimization type

- **Hyperparameter optimization**: core method is right, but training recipe needs tuning (LR, batch size, schedule, warmup)
- **Architecture tuning**: method concept is right, but implementation details need adjustment (layer count, hidden dim, attention heads)
- **Training recipe change**: data sampling, loss weighting, curriculum, augmentation
- **Bug fix**: the code has an error that explains the suboptimal results
- **Scale adjustment**: method works but needs different scale (more data, more compute, longer training)

## Step 1: Root Cause Diagnosis

### 1.0 Config Adequacy Check (MANDATORY — before diagnosing the method)

Before diagnosing the method or results, verify the experimental configuration was adequate. A failed experiment due to inadequate configuration is a setup failure, not a method failure.

Check:
- Output limits: Were generations truncated? If max_tokens was set too low for the task, results are invalid regardless of the method.
- Model scale: Was the model large enough for the claim? A claim about "LLM inference" tested only on a 0.5B model may not be credible.
- Batch size: Was it appropriate for the hardware? OOM failures from oversized batches are infrastructure issues.
- Seeds: Were enough seeds run for statistical validity? Single-seed results cannot support strong claims.
- Data quality: Were there issues with the dataset (corrupted files, wrong splits, preprocessing bugs)?
- Hyperparameters: Were learning rate, schedule, and other hyperparameters in reasonable ranges?
- Evidence authenticity: Is this experiment using real data and official evaluators? If the experiment was registered as prototype or pilot, its results cannot be iterated into claims. Re-register at evidence scale before investing optimization effort.

If the configuration was inadequate, fix it and re-run BEFORE diagnosing the method. Do not analyze results from a broken experiment.

### 1.1 Self-diagnosis

Before calling subagents, check the obvious:
- Read experiment logs: `inspire_logs(job_id="...", lines=200)`
- Check GPU metrics: `inspire_metrics(job_id="...", time_range="1h", mode="summary")`
- Look for: NaN losses, gradient explosions, training plateaus, data loading bottlenecks

### 1.2 Methodologist diagnosis

For non-obvious issues, deploy the methodologist. Follow reviewer independence protocol from `peer-review` skill if multiple diagnostic rounds are needed.

```
task(subagent_type="methodologist", background=true):
  "Diagnose why these experiment results are below expectations.

   PLAN: [paste plan's method thesis and expected metrics]

   RESULTS:
   [paste cross-experiment comparison table]

   EXPERIMENT DETAILS:
   [for each underperforming experiment: hyperparameters, training curves if available, final metrics]

   Analyze:
   1. Is this a hyperparameter issue (LR, batch size, schedule)?
   2. Is this an architecture issue (capacity, depth, width)?
   3. Is this a training recipe issue (data, loss, curriculum)?
   4. Is this a fundamental method limitation?
   5. What specific changes would most likely improve results?

   For each suggested change:
   - Expected impact (quantitative if possible)
   - Risk (could this make things worse?)
   - Compute cost

   Rank changes by expected_impact / compute_cost ratio."
```

### 1.3 Scholar search for optimization tricks

If the methodologist identifies a specific bottleneck, search for solutions:

## Step 2: Design Adjusted Experiments

### 2.1 Register new experiments linked to predecessors

For each optimization target, register a new experiment referencing the predecessor:

```
research_experiment(action="register",
  title="Main method — LR sweep 3e-4 (optimization of exp_001)",
  group="main",
  plan="plan_XXX",
  authenticity="evidence",
  redlines=["R1_metric_immutability"],
  backend="inspire",
  hyperparameters={learning_rate: 3e-4, batch_size: 128, seed: 42, ...})
```

Write the experiment `.md` with explicit links:
```markdown
## Optimization Context
- Predecessor: exp_001 (PPL 21.3, target was < 20.0)
- Change: LR 1e-4 → 3e-4
- Rationale: [from diagnosis]
- Expected outcome: PPL improvement of 0.5-1.5
```

### 2.2 Regression guard experiments

If making non-trivial code changes (not just hyperparameters), register a regression check:

```
research_experiment(action="register",
  title="Regression check — baseline with new code",
  group="sanity",
  ...)
```

### 2.3 Parallel vs sequential

**Run in parallel** (independent changes):
- Different hyperparameter values for the same experiment
- Different seeds for variance measurement
- Independent optimization targets

**Run sequentially** (dependent changes):
- Code change requires validation before further tuning
- Staged training where phase 2 depends on phase 1 output

## Step 5: Compare Old vs New

### 5.1 Cross-experiment comparison

```
research_experiment(action="compare",
  ids=[old experiment IDs + new experiment IDs])
```

### 5.2 Statistical rigor

Statistical testing thresholds from `config.experiment`: `significance_level` (default: 0.05), `min_seeds` (default: 3), `regression_tolerance` (default: 0.05).

| Seeds | Test | Interpretation |
|-------|------|----------------|
| ≥ `config.experiment.min_seeds` | Paired t-test or Wilcoxon | Report p-value and Cohen's d |
| 1-2 | Bootstrap CI (1000 resamples) | CI crosses zero → inconclusive |
| 1 | Do NOT claim improvement | Preliminary observation only |

### 5.3 Delta analysis

For each optimization target:

| Change | Old Metric | New Metric | Delta | Significant? | Assessment |
|--------|-----------|-----------|-------|-------------|------------|
| LR 1e-4 → 3e-4 | PPL 21.3 | PPL 19.8 | -1.5 | p=0.02, d=1.1 | Meaningful improvement |

### 5.4 Regression check

If code changes were made, verify the regression guard experiment:
- Baseline result should be within `config.experiment.regression_tolerance` (default: 5%) of original
- If regression detected: revert code change, try alternative

Record insights:
```
research_timeline(action="append_free_event", event_type="insight",
  summary="LR 3e-4 improves PPL by 1.5 (p=0.02). No regression on baseline.",
  event_refs=["exp_001", "exp_XXX"])
```

## Step 6: Decision

### 6.1 Assess against plan's evidence sets

Re-read the plan's kill set and sufficient set. With the new results:

- **Kill set passed AND sufficient set complete** → advance to compose (invoke claim-build)
- **Kill set passed, sufficient set incomplete** → need more experiments (may be supplement, may be another iteration)
- **Kill set failed** → method has fundamental issues → rollback to design
- **Results improved but not yet sufficient** → iterate again if rounds remain

### 6.2 Decision routing

**Advance to compose (claim-build):**
```
research_state(action="advance", target_phase="compose",  → then invoke claim-build skill
  summary="Building claims from experiment evidence",
  reason="Sufficient set complete after N optimization rounds. Key metric: [X].",
  refs_plan="plan_XXX",
  refs_experiments=[...all relevant exp IDs...])
```

**Iterate again** (if `config.experiment.max_optimize_rounds` not reached and results are improving):

Extend the DAG:
```
dagwrite({ nodes: [
  ...existing completed nodes...,
  { id: "analyze-r2", content: "Round 2: re-analyze with new results", status: "pending", deps: ["decide"] },
  { id: "diagnose-r2", content: "Round 2: refine diagnosis", status: "pending", deps: ["analyze-r2"] },
  ...
]})
```

Re-enter at Step 0 with the new results as input.

**Rollback to design** (method fundamentally doesn't work):
```
research_state(action="redirect", target_phase="design",
  summary="Method revision needed based on experiment optimization results",
  reason="After N optimization rounds, [key metric] remains at [X] vs target [Y]. Root cause: [Z].",
  refs_plan="plan_XXX")
```

**Rollback to explore** (direction is not viable):
```
research_state(action="redirect", target_phase="explore",
  summary="Re-exploring research direction",
  reason="Experiments show [fundamental limitation]. N optimization rounds did not help.",
  refs_idea="idea_XXX")
```

### Budget Exhaustion Decision Tree

When `enforceBudget` returns `must_decide` or `must_escalate`:

1. **must_escalate** (stagnation > max_stagnation):
   - First, try reframing the research question within the current phase
   - If reframing fails, add a `reasonableness_check` checkpoint and ask the user
   - If user confirms stagnation, redirect to design with a specific redesign request

2. **must_decide** (attempts > max_attempts OR escalation > max_escalations):
   - Review all experiment results holistically
   - If any results are promising: narrow scope and promote with qualified claims
   - If all results failed in the same way: redirect to design with diagnosis report
   - If mixed results: claim what you can, document what failed, promote with caveats

Do NOT simply abort — every experiment produces knowledge even when it "fails".

## Participation Mode Behavior

- **collaborative**: Pause after diagnosis (Step 1) to confirm optimization plan. Pause after results comparison (Step 5) to discuss findings. Pause at decision (Step 6).
- **guided**: Pause at decision (Step 6) only.
- **autonomous**: Run full cycle. Pause only on: all experiments fail, rollback needed, or `config.experiment.max_optimize_rounds` reached without improvement.

## Error Recovery

| Situation | Action |
|-----------|--------|
| No completed experiments (experiment-cycle never ran) | Redirect to experiment-cycle: `skill(name="experiment-cycle")` |
| All new experiments fail | Check if it's infrastructure (Inspire platform issue) vs code issue. For platform: retry with different spec/priority. For code: read logs, fix, resubmit. |
| Results worse after optimization | Revert to previous best configuration. The optimization target was wrong — reassess diagnosis. |
| Budget exhausted | Stop. Report remaining experiments needed. Suggest: low-priority CPU tasks (free), reduce scope, or use the best available results. |
| Experiment takes too long | Set agenda_watch and yield. Do NOT poll in a loop. |
| Code has uncommitted changes | REFUSE to submit. Git discipline is non-negotiable. |
| Optimization doesn't converge | After `config.experiment.max_optimize_rounds` rounds, the bottleneck is likely in the method, not the recipe. Recommend rollback to design with the diagnosis evidence. |

---

## Rollback Entry Points

### From compose (evidence insufficient)

1. Read which claims lack evidence
2. Design targeted experiments to fill the specific gap
3. Re-enter at Step 2 (design) — skip full diagnosis if the gap is clear

### From venue-cycle (reviewer demands more experiments)

1. Map each reviewer request to a specific experiment
2. Register and submit as a new optimization batch
3. Re-enter at Step 2 (design) with reviewer comments as input
