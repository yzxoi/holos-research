## Literature Discovery — `mcp__scholight__search_papers` (primary)

Use `mcp__scholight__search_papers` for ALL academic paper discovery in this skill (replaces the legacy arXiv search). The main agent or a visible subagent calls it directly.

Tool contract:
- `query` (required): a focused natural-language research question (task + method + domain/comparison).
- `strength`: use `"thorough"` for novelty-critical discovery; `"standard"` for quick iteration.
- `limit`: start at 5, raise to 10 for broad recall.
- `categories`: optional exact subject codes as an ARRAY (e.g. `["cs.AI", "cs.CL"]`) — never a string.
- `date_from` / `date_to`: optional `YYYY-MM-DD` bounds. For concurrent-work checks use `date_from` = 3 months ago.
- Preserve the returned rank order.

**Fallback discipline** (if scholight is unavailable/times out):
- Retry once with `strength: "standard"` and a narrower query.
- If still failing, fall back to `websearch`/`webfetch` on `https://arxiv.org/abs/...` or the arXiv search tool — never block the pipeline on a single tool.

**Paper Card contract** (for every closest work): `research_wiki(ingest_paper)` creates `papers/{slug}.md` as a template; then APPEND/EDIT:
- `## anchor_relevance` — where this paper sits relative to the idea (`closest work` / `foundation` / `competing mechanism`).
- `## transfer` — could the method/idea transfer to our direction? how, and what would BLOCK it? (one line if no clear transfer).
- `## evidence` — `html | full_text | partial | abstract_only`.
Ground every claim in the paper; never fabricate numbers/methods/results.

## Step 1: Closest-Work Identification

### 1.1 Targeted search — two tracks, parallel (scholight)

Deploy 2 parallel agents — one for **same-problem** work, one for **same-mechanism** work. Skip the generic industry search unless the idea is application-oriented. Both use `mcp__scholight__search_papers` with **3-4 queries each, `strength: "thorough"`, recall first** — cast a wide net so no close work is missed.

```
task(subagent_type="scholar", background=true):
  "You are the SameProblemScout. Find the most recent work (2025-2026) closest to
   this idea: [paste idea description and core insight].
   Use mcp__scholight__search_papers with 3-4 queries built from the idea's problem
   statement, strength='thorough', limit=10 each. Include a query restricted to the
   last 3 months (date_from) to catch concurrent pre-prints.
   For each candidate: arXiv id, title, one-line method, SPECIFIC overlap with our
   idea, date, venue. For the 2-3 most relevant: call
   research_wiki(action='ingest_paper', ...) and build a Paper Card
   (anchor_relevance/transfer/evidence sections) in .research/literature/papers/{slug}.md.
   Return: ranked closest-work shortlist with concrete overlap analysis."

task(subagent_type="scholar", background=true):
  "You are the SameMechanismScout. Find work that uses a similar MECHANISM to ours,
   even if applied to a different problem or domain.
   [paste the technical approach from idea description]
   Use mcp__scholight__search_papers with 3-4 queries built from the mechanism's core
   primitives (not the surface task), strength='thorough', limit=10 each.
   For each candidate: arXiv id, title, mechanism, domain, how it relates to our
   mechanism. For the 2-3 most relevant: ingest + build a Paper Card.
   Return: ranked mechanism-overlap shortlist."
```

### 1.2 Build closest-work shortlist

Identify the **2-3** most directly related papers. For each:
- What specific aspect overlaps with our idea?
- What is the precise technical difference?
- Why does that difference matter?

### 1.3 Ingest findings

Register any missed papers with `research_wiki(action="ingest_paper")`.
Establish relationships: `research_wiki(action="link", ...)`

## Step 2: Contribution Positioning

### 2.1 Classify contribution type

Pick the primary type. Do not over-classify — most papers are one type with supporting elements:

| Type | Core claim pattern |
|------|-------------------|
| **new method** | "We propose [mechanism] that [achieves what]" |
| **new problem** | "We identify [problem] that prior work overlooks" |
| **new analysis** | "We reveal [insight] about [existing method]" |
| **method transfer** | "We adapt [method X] to [domain Y]" |

### 2.2 Write contribution statement

Write a **concise** statement (4-8 sentences max) covering:

1. What we do and how it differs from closest work
2. The key insight (one sentence)
3. What this enables that was not achievable before
4. Scope: when this holds, when it doesn't

**Honesty rules:**
- Do NOT claim "first to apply X to Y" unless the adaptation is non-trivial
- Do NOT list more than 2 distinct contributions
- If the honest calibration is "weak", say so — then try reframing the contribution type

### 2.3 Build positioning table

| Paper | Overlap | Our difference | Why it matters |
|-------|---------|----------------|----------------|

2-3 rows (one per closest work), not 5. Each row has a concrete, verifiable difference.

## Step 3: Adversarial Review (single round, 2 lenses)

Deploy **2 agents in parallel** — one critic, one scholar. Not three. The goal is to catch real problems, not generate redundant feedback.

### 3.1 Critic: Devil's advocate + overclaim audit (combined)

```
task(subagent_type="critic", background=true):
  "Review this contribution statement for a top-venue submission:

   [paste contribution statement + positioning table]

   Apply these tests (combined devil's advocate + overclaim check):
   1. Reduction test: Could a reviewer say 'this is just [simple variant]'?
   2. Is this primarily engineering effort rather than insight?
   3. Are differences specific and verifiable, or vague ('more efficient')?
   4. Is the claim scope honest? Are there limiting assumptions?
   5. Contribution sprawl: more than 2 distinct claims?
   6. Is the comparison against the strongest prior work?

   For each: PASS / CONCERN / FAIL + specific feedback.
   Overall verdict: pass / revise / rethink.
   If rethink: suggest a concrete reframe direction.
   Return structured text. The main agent records via research_idea(action='review')."
```

### 3.2 Scholar: Novelty verification

```
task(subagent_type="scholar", background=true):
  "Verify the novelty of this contribution claim:
   [paste contribution statement]

   1. Use mcp__scholight__search_papers (strength='thorough') to search for any
      2025-2026 work making a similar claim or using a similar mechanism — 3-4 queries.
   2. Add a concurrent-work query restricted to the last 3 months (date_from).
   3. Verify each 'differs from' statement against the actual paper (read the closest
      works' Paper Cards or full text via mcp__scholight__extract_url).
   4. Is the contribution type classification correct?

   Return: per-claim novelty verdict (NOVEL / PARTIAL / SCOOPED) + corrections.
   For important papers: call research_wiki(action='ingest_paper', ...) + build Paper Card.
   For minor papers: return title/arxiv/venue as text."
```

### 3.3 Record reviews

```
research_idea(action="review", id="idea_XXX", reviewer="critic",
  focus="adversarial review", verdict="pass|revise|rethink",
  summary="<review summary>", scores={...},
  action_items=[...], review_body="<full review text>")
```

### 3.4 Drift check
After reviews: does this contribution still address the anchor? If positioning shifted the idea, update the anchor or flag for user.

---

## Step 4: Revise (max 1 round)

### 4.1 Parse feedback

Extract actionable items. Classify:
- **Must fix**: evidence-backed concerns
- **Consider**: reasonable but arguable
- **Wrong**: misunderstanding — push back

### 4.2 Revise

Update the contribution statement and positioning table. Re-check drift against anchor.

### 4.3 Decision

- If both reviewers pass → proceed to writeback
- If minor concerns → fix and proceed (no re-review)
- If critical concern remains after revision → present options to user: reframe, narrow scope, or rollback

Do NOT run a second full review round. The goal is to converge, not iterate endlessly.

## Step 6: Present to User

**⏸ CHECKPOINT — do not proceed without user input.**

**Checkpoint kind: `reasonableness_check`**

Present:
- Contribution statement (with type and honest strength calibration)
- Positioning table (2-3 closest works)
- Grounded StorySpine (grounded_angle, expected_main_claims, minimum_evidence)
- Key concerns from review (summarized in 1-2 sentences, not full text)

**Options for user**:
1. **Confirm** — advance to design
2. **Reframe** — try a different contribution angle before deciding
3. **Rollback to explore** — positioning not viable; record pivot rationale

## Error Recovery

| Situation | Action |
|-----------|--------|
| Contribution is overclaimed after revision | Downgrade strength, reframe type, or recommend returning to explore |
| Scholar finds scooped work | If core claim scooped → rollback to explore. If sub-claim → narrow scope |
| Drift detected | Present both directions to user for adjudication |
| Reviewers disagree | Present both assessments, let user decide |
| Phase rollback from design | Re-enter at Step 3 (review) with new information. Do NOT restart from Step 0 |
| scholight unavailable/times out | Retry with `strength: "standard"`; fall back to websearch/webfetch on arxiv.org or the arXiv search tool; never block the pipeline |

### Rollback Cleanup

When rolling back from ground to explore:
- Wiki edges created for the failed grounded idea should be noted but NOT deleted (they document the exploration path)
- Use `research_wiki(action="update_entry", id="...", notes="Grounding failed — contribution collapsed. Retained for reference.")` to mark
- Do NOT delete story spine files — they are valuable exploration artifacts
