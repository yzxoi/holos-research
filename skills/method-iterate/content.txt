## Step 1: Diagnose and Classify Feedback

### 1.1 Anchor drift check

Before any revision, verify: would the requested changes move the plan away from the anchor?

- **No drift**: the changes refine the mechanism within the same problem scope → proceed
- **Mild drift**: the changes slightly expand scope → flag but proceed with caveat
- **Severe drift**: the changes fundamentally change what problem is being solved → present to user, do NOT silently revise

### 1.2 Classify each feedback item

For each piece of feedback, classify:

| Category | Meaning | Action |
|----------|---------|--------|
| **mechanism** | Change the core method (loss, architecture, signal) | Revise method section |
| **simplification** | Remove or merge components | Reduce complexity budget |
| **addition** | Add new component | Check against `config.design.max_primary_claims` and complexity budget |
| **recipe** | Change training procedure (data, schedule, hyperparams) | Revise training plan |
| **scope** | Narrow or widen claims | Revise contribution focus + validation sketch |
| **feasibility** | Adapt to resource constraints | Revise compute estimate + method if needed |
| **experiment-driven** | Method change motivated by experiment results | Revise with empirical evidence |

### 1.3 Conflict detection

If multiple feedback items conflict (e.g., "simplify" + "add component X"), resolve:
- Experiment-driven feedback takes priority over theoretical preference
- User explicit instructions take priority over reviewer suggestions
- Simplification takes priority over addition unless the addition is experiment-justified

## Step 3: Adversarial Review

Deploy the critic with full context. The reviewer is stateless — include everything. Follow the reviewer independence protocol from `peer-review`: fresh task per round, no prior round findings in the prompt, cross-model for high-stakes reviews.

```
task(subagent_type="critic", background=true, dag_node_id="review"):
  "You are reviewing a REVISED method proposal for a top venue.
   This is revision round N — the plan was changed because: [feedback summary].

   Read the Problem Anchor first. If the revision caused drift, flag it.

   PROBLEM ANCHOR:
   [paste anchor]

   PREVIOUS VERSION SCORE: [paste score history]
   WHAT CHANGED: [paste changes summary]

   === REVISED PROPOSAL ===
   [paste full revised plan .md]
   === END PROPOSAL ===

   Score these dimensions (1-10):
   1. Problem Fidelity (15%): Does the method still attack the original bottleneck?
   2. Method Specificity (20%): Concrete enough to implement?
   3. Contribution Quality (20%): One dominant mechanism claim, real novelty, no sprawl?
   4. Frontier Leverage (10%): Uses current primitives appropriately?
   5. Impact Potential (15%): Would other researchers build on this?
   6. Feasibility (10%): Can this be built with stated resources?
   7. Validation Focus (5%): Experiments minimal but sufficient?
   8. Venue Readiness (5%): Sharp and timely?

   OVERALL SCORE (1-10): Weighted average.

   For each dimension < 7: specific weakness + concrete fix + priority (CRITICAL/IMPORTANT/MINOR).

   Also:
   - Simplification Opportunities: NONE if already tight.
   - Drift Warning: NONE or explanation.
   - Regression Check: Did the revision make anything WORSE compared to the previous version?
   - Verdict: READY / REVISE / RETHINK"
```

Record the review:
```
research_plan(action="review", id="plan_YYY",
  reviewer="critic",
  verdict="pass|revise|rethink",
  scores={problem_fidelity: N, method_specificity: N, contribution_quality: N,
    frontier_leverage: N, impact_potential: N, feasibility: N,
    validation_focus: N, venue_readiness: N, overall: N},
  summary="...",
  action_items=[...],
  review_body="...")
```

## Step 4: Convergence Check

### 4.1 Stop conditions

**Ready**: overall score ≥ `config.design.score_threshold` and verdict is READY and no unresolved drift → proceed to Step 5.

**Iterate**: score improved but not yet ready and rounds < `config.design.max_review_rounds` → extend DAG and loop back to Step 2 with reviewer feedback as input.

**Stalled**: score did not improve for 2 consecutive rounds → present to user with honest assessment:
- "The plan has plateaued at X/10. The remaining weakness is [Y]. Options: accept as-is, try a fundamentally different approach, or provide specific guidance."

**Rethink**: verdict is RETHINK → the revision made things worse or the direction is fundamentally off. Consider:
- Reverting to the previous plan version
- Rollback to `ground` if the contribution is unclear
- Rollback to `explore` if the direction is weak

### 4.2 Score tracking

Maintain a score history across rounds. If extending the DAG for another round, include the score trajectory in the next reviewer prompt.

```

```

## Participation Mode Behavior

- **collaborative**: Pause after diagnosis (Step 1) if anchor drift detected. Pause after revision (Step 2) to confirm changes. Pause at convergence (Step 4) each round.
- **guided**: Pause at convergence (Step 4) only when ready or stalled.
- **autonomous**: Run full review loop. Pause only on stall (2 rounds no improvement) or rethink verdict.

---

## Error Recovery

| Situation | Action |
|-----------|--------|
| No existing plan | Redirect to method-design: `skill(name="method-design")` |
| Experiment feedback contradicts plan assumptions | This is the most valuable feedback. Revise the plan with empirical evidence taking priority. |
| Reviewer and user feedback conflict | User feedback takes priority. Record the disagreement. |
| Score regression after revision | Revert: reactivate the previous plan. Analyze why the revision hurt. |
| Anchor fundamentally needs changing | Do not change silently. Block: `research_state(action="block", blocked_on="Anchor update needed based on [evidence]")` |
| MAX_ROUNDS without ready | Present best version. User decides: accept, continue manually, or rollback. User can increase `config.design.max_review_rounds` to continue. |
| Context compaction | Reload from plan `.md` files + `research_state(action="read")`. The plan `.md` is the full checkpoint. |

---

## Rollback Entry Points

### From experiment (method doesn't work)

1. Read experiment failure analysis from experiment `.md` files
2. The experiment results are hard evidence — they override theoretical expectations
3. Focus revision on the specific mechanism that failed, not the whole plan
4. If the failure is fundamental → consider rollback to explore

### From compose (evidence doesn't support claims)

1. Read which claims are unsupported
2. Narrow the claims in the validation sketch rather than adding complexity
3. May need to simplify the method to match what the evidence actually shows

### From venue-cycle (reviewer demands method changes)

1. External reviewer feedback has high priority
2. Re-enter at Step 1 with reviewer comments as feedback
3. Track: which external reviewer concerns map to which plan sections
